Offline Local Model Switchboard — Control Panel

Go 1 · Cobra 1 · Viper 1 · SQLite 3 (in the real tool) · Gateway 127.0.0.1:8080 · OpenAI-compatible POST /v1/chat/completions

Read first — what this is and is not: the Go command-line binary itself cannot run in a browser, so this page is not the Go binary. It is a working control panel that demonstrates the real switchboard logic: endpoint registration, profile routing, request validation, real forwarding attempts, and local logging. The spec lists a graphical user interface or web dashboard as out of scope, so this panel is a demonstration only, not part of the shipped command-line tool. Every reply on this page comes from one of two real paths only: (1) a real fetch to a registered local model server address, or (2) a real model running in this browser tab (WebLLM, Transformers.js version 3, or a GGUF file through wllama). If no model is loaded and no server answers, the panel reports the failure and never invents a reply. There is no test stub and no canned answer anywhere on this page. Search (section 6) ranks endpoints and usage-log rows with real BM25 (Robertson and Zaragoza, k1 1.5, b 0.75) and, when a local model is loaded, adds a one-sentence summary from that real model — never a canned answer, never a mock result.

0 · Local model — the real inference engine in this tab

This panel loads a real local model on its own when it opens — Transformers.js Qwen2.5-0.5B-Instruct first — so the built-in webllm:// endpoints can answer without a click. First load downloads the weights (about 350 megabytes for the 0.5B model, about 1 gigabyte for the 1.5B model), then the browser caches them. Inference runs on your device; your prompt is not sent to any cloud service by this page.

wllama loads a real GGUF file with llama.cpp compiled to WebAssembly. Paste a real file address or pick a file from your device. No default model address is filled in — an invented address would fail anyway.

6 · Search endpoints and usage log — real BM25 ranking + real model summary


Ranking is real BM25 (Robertson and Zaragoza: k1 1.5, b 0.75, Lucene-style inverse document frequency that is never negative), run locally over the endpoint registry and the usage log in section 4. There is no mock search here: the old of(mockResult) pattern from the api-integration-guide never existed in this panel, and this section does not add one. If you paste a live search backend address below, search calls it for real with a GET request and expects a SearchResult back; a failed call is reported, never silently replaced with a canned result. With no backend address, the real local search is BM25 ranking plus, when a model is loaded in section 0, a one-sentence summary from that real model — BM25 alone is never presented as an answer, and the model is never asked to rank on its own. Results follow the SearchResult shape: primaryContent, supportingMedia (image, video, or placeholder), metadata {source, timestamp, relevance}.













BM25 code lives in this page and in the repo folder as bm25.py (Python, with test_bm25.py) and bm25.js (same formula, same tests in bm25.test.js, run with node --test bm25.test.js). One difference: JavaScript /\w+/ matches ASCII word characters only, while Python re also matches Unicode letters; identical results for the ASCII text searched here. The guide's Angular steps (injecting HttpClient in search.ts) do not apply to this standalone page; the equivalent here is a real fetch GET with ?q=, and the backend address belongs in the field above, not hard-coded.

Exit codes 0 to 4


CodeMeaning


0Command completed as requested


1General error — missing config file, invalid flag value, failed database write; error printed to standard error


2Usage error — missing required flag or unknown subcommand

Config precedence (highest first)


  1. Command-line flags
  2. Environment variables with the SWITCHBOARD_ prefix, for example SWITCHBOARD_LISTEN
  3. Config file
  4. Built-in defaults


Config file search order: path from --config, then ./switchboard.yaml in the working directory, then $HOME/.config/switchboard/switchboard.yaml. Values merge by key; a higher source replaces only that key.


Phase 7 hardening limits


  • Request body cap: 10 megabytes → HTTP 413 above it
  • At most 100 requests at the same time → HTTP 429 above it
  • Unreachable endpoint → HTTP 502 · no healthy endpoint for the active profile → HTTP 503
  • Missing model field or malformed JSON → HTTP 400, and no usage row is written
  • Health probe every 30 seconds; a health state older than 60 seconds is stale
  • Gateway stays running after every failure case; usage rows are never lost for completed requests


Non-goals (spec): hosting or running model inference itself; proxying to cloud model providers or cloud billing; a graphical user interface or web dashboard; fine-tuning, training, or evaluating models; multi-user authentication, single sign-on, or team access control.
